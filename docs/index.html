MCP server + CLI · for cob-rag-engine · MIT

Your business's knowledge, in every agent.

cob-rag-mcp is an MCP server and a full CLI for cob-rag-engine, the self-hosted knowledge layer for AI assistants and agents. Plug a business's own knowledge base into Claude, Cursor, VS Code, n8n or any MCP client, or work with it straight from the shell. One set of 52 tools, two ways in.

npx -y cob-rag-mcp start

# or install both commands, then sign in
npm i -g cob-rag-mcp
cob-rag-engine login --url http://127.0.0.1:8000 --key ck_...

Who it's for

Agents over MCP. People in the shell.

An agent is only as useful as what it knows about the business it works for: the returns policy, the price list, which tests need fasting. cob-rag-engine holds that knowledge, one isolated knowledge base (a corpus) per business. This package puts it where agents and people work.

MCP server · cob-rag-mcp start

In any MCP client

Claude, Cursor, VS Code, n8n, any client that speaks MCP.

  • The agent calls search to pull the right passages, with sources, and answers from them with its own model.
  • Or it calls ask for a complete cited answer written by the model configured in your engine.
  • Destructive tools are hidden unless you allow them with COB_RAG_ALLOW_DESTRUCTIVE=true.

Setup

You host the engine. No hosted service, ever.

cob-rag-mcp is only a client. It talks to a cob-rag-engine that you run yourself, on your laptop, your server or your cloud, using the URL and key you give it. Nothing is sent anywhere else.

  1. Run the engine

    One docker compose up. Start with the engine's quick start, then come back. New to it? The engine's site has the overview.

  2. Get a key

    The admin key (RAG_ADMIN_API_KEY in the engine's .env), a tenant key (tk_...) or a corpus key (ck_...). Which one?

  3. Install

    npx -y cob-rag-mcp start with nothing installed, or npm i -g cob-rag-mcp for both commands. Needs Node.js 22 or newer.

  4. Point it at the engine

    Set COB_RAG_URL and COB_RAG_API_KEY, or save them once with cob-rag-engine login.

For ask, a model must be configured in the engine (engine default, per corpus, or per request with your own key). search needs no model at all.

HTTP mode, the rules

Every request

Carries the caller's own engine key, as Authorization: Bearer <key> or X-API-Key: <key>. A request without a key gets 401, unless you set COB_RAG_HTTP_USE_SERVER_KEY=true on purpose.

Stateless

One fresh MCP server per request, so it scales horizontally and needs no sticky sessions. Callers may send their own X-LLM-* headers; the server's model key is never spent on a caller's behalf.

Bind

Binds 127.0.0.1 by default and, on loopback, refuses requests whose Host or Origin is not local. Bind wider and put TLS in front: keys travel in headers.

Docker

HTTP mode
docker build -t cob-rag-mcp .
docker run --rm -p 127.0.0.1:3333:3333 \
  -e COB_RAG_URL=http://host.docker.internal:8000 \
  cob-rag-mcp

The engine URL must be reachable from the container: host.docker.internal for an engine on the host, or the engine's service name on a shared Docker network.

Any other stdio client

Command npx, arguments -y cob-rag-mcp start, plus the COB_RAG_* environment variables. With a global install, the command is simply cob-rag-mcp start.

If a client shows the server as failed, run npx -y cob-rag-mcp start in a terminal with the same environment: the reason is printed on stderr.

The tools

52 tools, only the ones your key can use.

Each tool is one definition that is both an MCP tool and a CLI command. The server registers only the tools the key can use, and hides destructive ones unless allowed. With a tenant or admin key, tools that act on one corpus need a corpus_id (or a COB_RAG_CORPUS_ID default); a corpus key never sees that field.

Tool annotations match: readOnlyHint on reads, destructiveHint on destructive tools, openWorldHint: false everywhere, because every call goes to your own engine. --read-only leaves only the read tools. One prompt is included, answer-with-citations: search first, answer only from the passages, cite each source. Request and response shapes are typed from the engine's OpenAPI spec, so the tools cannot drift from the API. cob-rag-engine tools prints every tool and which keys can use it.

The CLI

The same tools, from the shell.

cob-rag-engine <command> [options]. Global options: --url, --key, --config, --json, --yes, --read-only. Every command has --help. Exit codes: 0 success, 1 engine or configuration error, 2 invalid input.

Sign in, check the key

cob-rag-engine login --url http://127.0.0.1:8000 --key ck_...
# Logged in to http://127.0.0.1:8000 with ck_****a1b2
# kind         corpus
# corpus_name  acme-faq
cob-rag-engine whoami
cob-rag-engine config show          # every setting, its source, secrets masked
cob-rag-engine config get api_key   # ck_****a1b2
cob-rag-engine config set corpus_id 7b221003-...
cob-rag-engine config path

login checks the key with the engine's /api/v1/whoami before saving anything, and writes the config file owner-only (0600). Leave --key out at a terminal and it prompts without echoing.

Search and ask

cob-rag-engine search "How long should I fast before a cholesterol test?" --final-k 3
# [1] Fasting before a lipid profile [faq-fasting-lipid]  (score 0.066)

cob-rag-engine ask "Do I need to fast for a thyroid test?"
# No, you do not need to fast for a thyroid test. ... [1]
#
# Sources:
#   [1] Thyroid test (TSH, T3, T4) [faq-thyroid]

cob-rag-engine ask "..." --stream          # prints as it is generated
cob-rag-engine ask "..." --stream --json   # raw events, one JSON object per line

search returns passages with sources and needs no model. ask returns a cited answer from the engine's model. Streaming is a CLI feature: an MCP tool call returns one result.

Keys

The key decides the reach. Give an agent the narrowest one.

The server asks the engine who the key is and offers only the tools that key can use. The engine enforces scope on every request; this package also hides what a key cannot use, so an agent is not tempted to try.

KeyPrefixWhat it reachesGive it to an agent?
Corpus keyck_One knowledge base and nothing else: search, ask, documents, ingest, settings, usage, feedback, widget keys.Yes, this is the default. A corpus key for one knowledge base.
Tenant keytk_Manages that tenant's corpora, its team, its own plan and record. Can rotate its own key.Only when the agent must create or manage corpora.
Admin keyRAG_ADMIN_API_KEYRuns the engine: tenants, plans, sign-up mode and branding, every corpus.Almost never.
Rule of thumb

Start with ck_

Hand the agent the corpus key for the one knowledge base it works on, add --read-only if it should only look things up, and leave destructive tools off.

Shown once

Store keys when you see them

create_corpus, create_tenant and every rotate_* return the new key in the tool result, because that is the only time the engine reveals it.

Widget keys

pk_ is a different thing

Widget keys (list_widget_keys, create_widget_key, revoke_widget_key) are for a corpus's website widget, and come with an embed snippet.

Security

Safe defaults, so an agent can't do much harm.

From the README and SECURITY.md.

  • Keys stay on your machineThey go to your engine and nowhere else. The config file is owner-only; config show, login and every log line mask keys (ck_****a1b2).
  • Destructive tools are off over MCPDeleting documents or corpora, revoking widget keys, rotating keys and suspending, declining or deleting tenants appear only with COB_RAG_ALLOW_DESTRUCTIVE=true. The CLI asks before each one, and refuses when it cannot ask unless you pass --yes.
  • Read-only mode--read-only or COB_RAG_READ_ONLY=true hides every write tool from MCP clients and makes the CLI refuse every write.
  • Uploads over MCP are fencedupload_file exists over MCP only on stdio and only when COB_RAG_UPLOAD_DIR is set. Paths are resolved, symlinks included, and anything outside that directory is refused, so a prompt-injected agent cannot ship your SSH keys into a knowledge base. Use a dedicated folder, never your home directory.
  • HTTP mode never lends a keyEach request brings its own. Keep the default 127.0.0.1 bind, or put TLS and a firewall in front of it. Leave COB_RAG_HTTP_USE_SERVER_KEY off unless every client that can reach the port should act with that key.
  • rotate_my_tenant_key cuts off the key in useThe server's own key is dead the moment it succeeds; restart it with the new key. The CLI warns first and offers to save the new key.
  • Never commit keysPrefer cob-rag-engine login, which prompts without echo, or your MCP client's secret inputs, over pasting keys into files.
  • Report vulnerabilities privatelyDo not open a public issue. Use GitHub Private Vulnerability Reporting or callobuzz@gmail.com; expect a first response within 48 hours. Engine vulnerabilities go to cob-rag-engine.
